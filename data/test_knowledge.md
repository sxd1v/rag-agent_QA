# RAG 基础概念

## 什么是 RAG

RAG（Retrieval-Augmented Generation）是一种结合检索和生成的技术架构。它让大语言模型在回答问题时，先从知识库中检索相关文档，再基于检索结果生成答案。这样可以有效缓解大语言模型"幻觉"问题，让答案有据可查。

## RAG 的核心流程

RAG 的核心流程分为四个步骤：
1. **文档加载**：将 PDF、Markdown、HTML 等格式的文档加载为统一格式
2. **文档分块**：将长文档切分成适合检索的小段落（chunk）
3. **向量化存储**：将每个 chunk 转换为向量，存入向量数据库
4. **检索生成**：用户提问时，先检索相关 chunk，再送入 LLM 生成答案

## Chunk 的选择策略

Chunk size（块大小）是 RAG 效果的关键参数之一。常见的分块策略包括：

- **固定大小分块**：按字数或段落数固定切分，简单但可能破坏语义完整性
- **按语义分块**：根据文本的语义边界（如段落、章节）切分，保留更好的上下文
- **递归分块**：先用大的语义单元分割，不合适时再递归细分

一般建议 chunk size 在 300-500 字之间，overlap（重叠）在 20-50 字之间，以保留边界信息。

## Embedding 模型选择

Embedding 模型负责将文本转换为向量。常用的选择包括：

- **BGE**：国产优秀模型，中文效果好，支持多种维度
- **Sentence-Transformers**：开源生态丰富，适合英文场景
- **MiniMax Embedding**：国产商业模型，针对中文场景优化

选择模型时要考虑：语言、维度（常见 768/1024/1536）、效果、速度。

## 向量数据库

常见的向量数据库有：

- **Chroma**：轻量级，易用性强，适合快速原型
- **FAISS**：Meta 开源，适合大规模向量检索
- **Milvus**：国产，分布式支持好，适合生产环境
- **Qdrant**：Rust 实现，性能高，支持混合检索

## 检索策略

基础的检索策略是向量相似度检索（top-k），但有多种优化方式：

- **Query Rewrite**：改写用户问题为更利于检索的形式，如同义词扩展、问题分解
- **Hybrid Retrieval**：结合关键词检索（如 BM25）和向量检索，取并集或交集
- **Rerank**：先用向量检索召回候选集，再用重排模型优化排序

## Query Rewrite 的作用

Query Rewrite（查询改写）是改善检索召回率的重要技术。当用户问题与知识库文档表述不一致时，直接检索可能效果不佳。

Query Rewrite 的常见方法：
1. **同义词扩展**：将问题中的关键词扩展为同义词，如"电脑"→"计算机/PC"
2. **问题分解**：将复杂问题拆分为多个简单问题分别检索
3. **术语标准化**：将口语化表达转为标准术语

## Context 构建

检索到相关 chunk 后，需要构建适合 LLM 消费的 Context：

- **去重**：同一内容可能多次召回，需要去重
- **排序**：将最相关的 chunk 放在前面（LLM 对开头和结尾的内容记忆更强）
- **长度控制**：Context 不能超过 LLM 的上下文窗口限制，需要截断或分批处理

## 生成阶段优化

生成答案时，可以从以下方面优化：

- **Prompt 优化**：明确要求模型"仅基于提供的证据回答"，减少幻觉
- **溯源标注**：让模型在回答中标注参考了哪个 chunk
- **无法回答时的处理**：当检索结果不足以回答时，模型应如实说明而非编造

## RAG 的局限性

RAG 虽然强大，但也有局限：

- **召回质量问题**：如果检索不到正确答案，后续生成一定失败
- **Context 长度限制**：LLM 上下文窗口有限，不能无限输入 chunk
- **多跳推理**：复杂问题需要多步推理时，单次检索可能不够，需要 Agent 循环
- **知识库时效性**：知识库内容可能过时，需要定期更新
